# Personal Harness V1.3 — Stage 2 Multi-Agent Intelligence Architecture

> **Status: PLANNED / DO NOT IMPLEMENT YET**
>
> Stage 2 must **not** begin until V1.3 Stage 1 has been completed, validated, and stabilized. This document is an architecture/planning baseline only and does not authorize changes to the current implementation.

## 1. Stage 2 Goal

Stage 2 upgrades Personal Harness from a primarily DeepSeek-driven workflow into a layered multi-agent system.

The intended high-level relationship is:

```text
                    User
                     │
                     ▼
             GPT Main Agent
        (conversation + reasoning)
                     │
             Harness Orchestrator
               /             \
              ▼               ▼
      DeepSeek Agent          Jev
      Execution Layer    Fast/Local Layer
              \               /
               └──── Tools ───┘
```

The core design principle is:

> **GPT understands and coordinates; DeepSeek executes; Jev handles suitable fast/local/computer-interaction tasks.**

This is a role preference, not a hard-coded limitation. The orchestration layer should remain flexible enough to route tasks according to capability, latency, cost, availability, and future model changes.

## 2. GPT — Main Agent / Primary User Interface

GPT becomes the primary high-level agent that the user normally talks to inside Harness.

Responsibilities:

- Hold the main conversation with the user.
- Understand natural-language requirements, including incomplete or iterative requests.
- Use available project/context information to clarify the user's actual goal.
- Convert user intent into structured plans and executable tasks.
- Decompose complex work into smaller tasks.
- Decide whether work should be handled directly, delegated to DeepSeek, delegated to Jev, or split across multiple agents.
- Coordinate multi-step workflows and dependencies.
- Communicate directly with the DeepSeek execution layer through an internal agent-to-agent protocol.
- Review important outputs returned by execution agents before presenting results to the user.
- Request revisions or additional execution when results do not satisfy the original requirement.
- Remain the main conversational context owner wherever practical.

The desired normal interaction path is therefore:

```text
User ↔ GPT ↔ DeepSeek
          ↕
         Jev
```

DeepSeek does not need to be the normal user-facing conversational agent once this architecture is active.

## 3. DeepSeek — Execution Layer

DeepSeek remains a major component of Harness, but its primary role shifts toward execution.

Typical responsibilities:

- Coding and implementation.
- Repository/file modifications.
- Terminal tasks.
- Debugging.
- Running tests and interpreting routine failures.
- Refactoring.
- Repetitive or high-volume engineering work.
- Git/GitHub-related implementation tasks when appropriate.
- Executing structured tasks produced by GPT.
- Returning machine-readable results, changed-file summaries, test status, errors, and blockers to GPT.

A typical task flow should look like:

```text
User request
   ↓
GPT understands requirement
   ↓
GPT creates implementation task
   ↓
DeepSeek executes
   ↓
DeepSeek returns result/report
   ↓
GPT reviews result
   ├─ acceptable → report to user
   └─ incomplete → send revision/fix task back to DeepSeek
```

This allows DeepSeek to remain the cost-effective high-volume execution engine without requiring it to own every high-level conversation and architectural decision.

## 4. Jev — Fast / Local / Computer Interaction Layer

Jev remains part of Stage 2 and should focus on tasks where a fast/local decision layer or computer interaction is more suitable than repeatedly invoking a large cloud model.

Candidate responsibilities include:

- Computer Use.
- GUI interaction and desktop control.
- Fast local decisions.
- Screen/input-response loops where low latency matters.
- Lightweight routing or immediate reactions.
- Suitable local automation tasks.
- Other tasks discovered during implementation where Jev has a clear latency, privacy, interaction, or efficiency advantage.

Jev should **not** be forced to compete with DeepSeek for general coding work or with GPT for the main user conversation. Its role should be capability-driven.

## 5. Agent-to-Agent Communication

Stage 2 should introduce a structured internal communication protocol rather than passing arbitrary conversational text between agents.

A delegated task should be able to carry fields such as:

```yaml
task_id: <id>
source_agent: gpt-main
target_agent: deepseek-executor
type: implementation
objective: <clear objective>
context: <relevant project context>
constraints:
  - <constraint>
deliverables:
  - <expected output>
verification:
  - <test/review requirement>
```

Execution agents should return structured status information such as:

```yaml
task_id: <id>
status: completed | partial | blocked | failed
summary: <what was done>
changed_files: []
tests: []
blockers: []
follow_up: []
```

The exact schema is intentionally not frozen yet. Stage 2 implementation should validate it against the actual Harness/DSH architecture before locking the protocol.

## 6. Model Provider Abstraction

GPT must **not** be hard-coded throughout Harness.

Stage 2 should introduce or extend a provider/model abstraction so the role and the provider are separate concepts.

Conceptually:

```yaml
agents:
  main:
    role: orchestrator
    provider: openai
    model: configurable

  executor:
    role: execution
    provider: deepseek
    model: configurable

  fast_local:
    role: computer_interaction
    provider: jev
    model: configurable
```

The purpose is to allow future replacement or addition of providers (for example Claude or later models) without redesigning the entire Harness architecture.

Model selection should ultimately be configurable rather than tied permanently to a specific model version.

## 7. Routing Principles

The orchestrator should eventually consider:

- task type;
- required capability;
- latency;
- API/token cost;
- context requirements;
- privacy/local-processing requirements;
- tool availability;
- current provider availability;
- previous execution result;
- whether human confirmation is required.

Example routing intentions:

```text
Conversation / requirement understanding → GPT
Complex planning / orchestration         → GPT
High-volume implementation               → DeepSeek
Coding / debugging / testing             → DeepSeek
Computer Use / GUI interaction           → Jev
Fast local response loop                 → Jev
Final high-level review                  → GPT
```

These are defaults, not absolute rules.

## 8. Stage Boundary

### Stage 1

Continue the existing V1.3 Stage 1 work. Do not change its scope merely to prepare this Stage 2 architecture unless a small compatibility decision is clearly necessary and separately approved.

### Stage 2

Only after Stage 1 is complete and stable:

1. Audit the real Stage 1 architecture and current DSH/Harness extension boundaries.
2. Confirm the safest provider abstraction and agent communication mechanism.
3. Add GPT provider/API support without embedding credentials in source code.
4. Introduce GPT as the configurable Main Agent / Orchestrator.
5. Define GPT ↔ DeepSeek structured delegation and result-return flow.
6. Integrate Jev for suitable Computer Use / fast-local tasks.
7. Add routing, failure handling, cancellation, timeout, and fallback behavior.
8. Add observability so the user can understand which agent is working and why.
9. Test agent handoffs, context boundaries, cost controls, permissions, and failure recovery.
10. Keep the architecture provider-neutral so additional providers can be introduced later.

## 9. Safety / Engineering Constraints

- Never store API keys or access tokens in the repository.
- Do not silently send unnecessary local/private context to cloud providers.
- Tool execution and destructive actions must preserve existing Harness permission/approval boundaries.
- Agent delegation must be observable and interruptible.
- Prevent infinite agent-to-agent loops and uncontrolled API spending.
- Add task budgets / iteration limits before enabling autonomous recursive delegation.
- Fail safely when a provider is unavailable.
- Preserve rollback capability during Stage 2 migration.

## 10. Definition of Success

Stage 2 is successful when the user can primarily communicate with GPT as the Harness Main Agent; GPT can understand and coordinate the user's work; DeepSeek can receive structured execution tasks directly from GPT and return results for review; Jev can handle appropriate Computer Use/fast-local tasks; and all three operate through a maintainable orchestration layer rather than three disconnected chat interfaces.
